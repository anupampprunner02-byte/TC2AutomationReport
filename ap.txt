================================================================================
 1. PROJECT OVERVIEW
================================================================================

This is a generic, production-ready Playwright + TypeScript end-to-end test
automation framework. It is designed to be cloned and adapted for any web
application with minimal configuration effort.

Key capabilities:
 - Page Object Model (POM) for maintainable, reusable test code
 - AI-assisted test generation via Claude Code slash commands
 - Playwright MCP integration for live browser inspection
 - Auth session caching (login once, reuse across all tests)
 - Allure + HTML reporting with automatic screenshots
 - Excel-based test case import and progress tracking
 - 6-layer knowledge system to avoid re-discovering known patterns

Repository: https://github.com/manishamrinal/ai-qa-ecosystem

 4. STEP-BY-STEP SETUP FROM SCRATCH
================================================================================

STEP 1 — Clone or initialize the repository
─────────────────────────────────────────────
  git clone https://github.com/manishamrinal/ai-qa-ecosystem.git my-project
  cd my-project

  OR create fresh:
  mkdir my-project && cd my-project
  git init
  npm init -y

STEP 2 — Install all dependencies
────────────────────────────────────
  npm install
  npx playwright install

  This installs Playwright browsers (Chromium, Firefox, WebKit).

STEP 3 — Configure environment variables
─────────────────────────────────────────
  cp .env.example .env

  Edit .env and set:
    LOGIN_EMAIL=your-test-user@example.com
    LOGIN_PASSWORD=your-test-password
    BASE_URL=https://your-app.example.com

STEP 4 — Configure application URLs
──────────────────────────────────────
  Edit src/data/allURL.ts:
  - Replace localhost:3000 URLs with your app's actual URLs
  - Add new URL entries for each page you want to test

STEP 5 — Configure auth setup
────────────────────────────────
  Edit src/fixtures/auth.setup.ts:
  - Update login page selectors to match your app
  - Update the post-login URL pattern in waitForURL()
  - Update login button text/selector

STEP 6 — Configure test data
──────────────────────────────
  Edit src/data/testdata.json:
  - Add test data for your application
  - Use $ENV_VAR placeholders for any sensitive values
  - Keep invalidUser data for negative test cases

STEP 7 — Configure Claude Code (if using AI assistance)
─────────────────────────────────────────────────────────
  Edit .claude/agents/app-config.md:
  - Fill in your application name and environment
  - Document your auth method
  - Add your URL catalog
  - Document page objects as you build them

STEP 8 — (Optional) Import test cases from Excel
──────────────────────────────────────────────────
  npm run tc:parse -- MyTestCases.xlsx

  Excel columns expected:
    Module | Function/Screen | Scenario | User Entity | User Role |
    Preconditions | Test Steps | Expected Result | Test Data

STEP 9 — Discover pages and scaffold page objects
────────────────────────────────────────────────────
  In Claude Code:
    /discover-page https://your-app.example.com/login
    /discover-page https://your-app.example.com/dashboard

  This uses Playwright MCP to inspect live pages and auto-generates:
    - src/locators/<feature>.locators.ts
    - src/pages/<feature>.page.ts

STEP 10 — Write tests
───────────────────────
  Manually (copy example files) OR via Claude Code:
    /write-test TC01
    /write-test "Login with valid credentials shows dashboard"
    /next-test

STEP 11 — Run tests
─────────────────────
  npm test                                              # all tests
  npx playwright test src/tests/login.spec.ts --project=chromium-no-auth
  npx playwright test src/tests/dashboard.spec.ts --project=chromium

STEP 12 — Generate reports
────────────────────────────
  npm run allure:generate && npm run allure:open
  npx playwright show-report

# Claude Code Instructions

Playwright + TypeScript QA automation framework using Page Object Model.
Read these files in order before doing anything:

1. **`.claude/agents/playwright-agent.md`** — Framework rules: POM conventions,
   test structure, locator priority, anti-patterns
2. **`.claude/agents/app-config.md`** — App-specific config: auth, URLs,
   test case tracking, run commands
3. **`.claude/agents/knowledge-layer.md`** — 6-layer knowledge check system

## Getting Started with a New Application
1. Copy `.env.example` to `.env` and add your credentials
2. Update `src/data/allURL.ts` with your app's URLs
3. Update `src/fixtures/auth.setup.ts` with your login flow
4. Update `src/data/testdata.json` with your test data
5. Update `.claude/agents/app-config.md` with your app details
6. Use `/discover-page <url>` to explore pages and scaffold page objects
7. Use `/write-test <description>` to implement test cases

## Custom Slash Commands
- `/write-test <id or description>` — Full workflow: implement → run → mark done
- `/discover-page <url or page name>` — MCP explore → scaffold locators + page obj
- `/next-test` — Pick up next pending test case and implement it
- `/heal-test <file or TC id>` — Diagnose and fix failing tests

## Project Conventions
- **Imports**: Always use `src/fixtures/baseTest.ts`, never `@playwright/test`
- **Test data**: `import testData from '../data/testdata'` (NOT testdata.json)
- **Secrets**: Use `$ENV_VAR` placeholders in testdata.json, values in .env
- **Test naming**: `TCXX - description` pattern
- **Page Object Model**: Locators in `src/locators/`, pages in `src/pages/`

import rawData from './testdata.json' with { type: 'json' };

function resolveEnvVars(obj: unknown): unknown {
  if (typeof obj === 'string' && obj.startsWith('$')) {
    const envKey = obj.slice(1);
    const value = process.env[envKey];
    if (!value) throw new Error(
      `Environment variable ${envKey} is not set. Check your .env file.`
    );
    return value;
  }
  if (Array.isArray(obj)) return obj.map(resolveEnvVars);
  if (obj !== null && typeof obj === 'object') {
    return Object.fromEntries(
      Object.entries(obj).map(([k, v]) => [k, resolveEnvVars(v)])
    );
  }
  return obj;
}

const testData = resolveEnvVars(rawData) as typeof rawData;
export default testData;

  NOTE: This file resolves all $ENV_VAR placeholders recursively.
  ALWAYS import from testdata.ts, never from testdata.json directly.

import { Page } from '@playwright/test';

export class ExampleLocators {
  readonly page: Page;

  constructor(page: Page) {
    this.page = page;
  }

  // Section — Form inputs
  get emailInput() {
    return this.page.locator('input[name="email"]');
  }

  get passwordInput() {
    return this.page.locator('input[name="password"]');
  }

  // Section — Actions
  get submitButton() {
    return this.page.getByRole('button', { name: 'Submit' });
  }

  // Section — Feedback
  get successMessage() {
    return this.page.getByRole('alert').filter({ hasText: 'Success' });
  }

  get errorMessage() {
    return this.page.getByRole('alert').filter({ hasText: 'Error' });
  }
}

  RULES:
  - One class per page/feature
  - Constructor takes Page, assign to readonly this.page
  - Each locator is a getter (lazy evaluation = fresh element each call)
  - Group related locators with // Section — Comment
  - Use locator priority: getByTestId > getByRole > getByLabel > CSS
  - Never define locators in page objects or test files

import { Page, expect } from '@playwright/test';
import { ExampleLocators } from '../locators/example.locators';
import { takeScreenshot } from '../utils/screenshotUtils';

export class ExamplePage {
  readonly page: Page;
  readonly locators: ExampleLocators;

  constructor(page: Page) {
    this.page = page;
    this.locators = new ExampleLocators(page);
  }

  async navigate(url: string) {
    await this.page.goto(url, { waitUntil: 'domcontentloaded' });
  }

  async verifyPageLoaded() {
    await expect(this.locators.emailInput).toBeVisible();
    await expect(this.locators.submitButton).toBeVisible();
  }

  async fillEmail(email: string) {
    await this.locators.emailInput.fill(email);
  }

  async fillPassword(password: string) {
    await this.locators.passwordInput.fill(password);
  }

  async submit() {
    await expect(this.locators.submitButton).toBeEnabled({ timeout: 10000 });
    await this.locators.submitButton.click();
  }

  async verifySuccess() {
    await expect(this.locators.successMessage).toBeVisible({ timeout: 10000 });
  }

  async verifyError(expectedText?: string) {
    await expect(this.locators.errorMessage).toBeVisible({ timeout: 10000 });
    if (expectedText) {
      await expect(this.locators.errorMessage).toContainText(expectedText);
    }
  }

  async takeScreenshot(name: string) {
    return await takeScreenshot(this.page, name);
  }
}

  RULES:
  - Each method = one logical user action
  - Verify methods use expect() for element state checks
  - Never put business logic in test files — all here
  - Always include takeScreenshot() convenience method
  - Instantiate locators class in constructor

export function getTimestamp(): string {
  const date = new Date();
  const yyyy = date.getFullYear();
  const mm = String(date.getMonth() + 1).padStart(2, '0');
  const dd = String(date.getDate()).padStart(2, '0');
  const hh = String(date.getHours()).padStart(2, '0');
  const min = String(date.getMinutes()).padStart(2, '0');
  const ss = String(date.getSeconds()).padStart(2, '0');
  return `${yyyy}${mm}${dd}_${hh}${min}${ss}`;
}

 10. SLASH COMMAND WORKFLOWS

/write-test <id or description>
─────────────────────────────────
PURPOSE: Implement a test case end-to-end (locators + page obj + spec)

WORKFLOW:
  1. Parse input — if numeric ID, run `npm run tc:show -- <id>`
                   if description, use directly
  2. Walk knowledge layers (see Section 20)
  3. Inspect live page via MCP (only if layers 1-5 insufficient)
  4. Decide file strategy (add to existing or create new)
  5. Implement in order:
     a. src/locators/<feature>.locators.ts
     b. src/pages/<feature>.page.ts
     c. src/tests/<feature>.spec.ts
     d. src/data/testdata.json (if new test data needed)
     e. src/data/allURL.ts (if new URLs needed)
  6. Run: npx playwright test src/tests/<file>.spec.ts --project=chromium
  7. Update page-knowledge.json with non-obvious findings
  8. Mark done: npm run tc:done -- <id>
  9. Show progress: npm run tc:status

/discover-page <url or page name>
───────────────────────────────────
PURPOSE: Explore a page and auto-scaffold locators + page object

WORKFLOW:
  1. Navigate via MCP: browser_navigate to URL
  2. Snapshot via MCP: browser_snapshot (full accessibility tree)
  3. Identify all interactive elements (inputs, buttons, dropdowns, grids)
  4. Test interactions via MCP: browser_click, browser_fill_form, etc.
  5. Update knowledge base:
     - test-management/page-knowledge.json (patterns, behaviors, quirks)
     - src/locators/<feature>.locators.ts (create or update)
     - src/pages/<feature>.page.ts (create or update)
  6. Report: elements found, files created/updated

/next-test [count]
────────────────────
PURPOSE: Pick up and implement the next pending test case(s)

WORKFLOW:
  1. Run npm run tc:next to get next pending test case
  2. If count > 1, implement each sequentially
  3. For each: run /write-test workflow
  4. After each: mark done/skipped, then fetch next
  5. Show final summary with IDs and outcomes

/heal-test <file or TC id>
────────────────────────────
PURPOSE: Diagnose and fix failing tests

WORKFLOW:
  1. Resolve target (spec file, TC ID, or specific test)
  2. Run tests and capture all failures
  3. For each failure:
     a. Read error — identify line, assertion, error type
     b. Check knowledge layers (known quirk? outdated locator?)
     c. Use MCP if selector needs live DOM inspection
  4. Fix in correct layer:
     - Wrong selector → src/locators/<feature>.locators.ts
     - Wrong interaction/wait → src/pages/<feature>.page.ts
     - Wrong assertion → page object verify method
     - Wrong test data → src/data/testdata.json
     - Wrong URL → src/data/allURL.ts
  5. Re-run to verify fix
  6. Update page-knowledge.json with non-obvious findings
  7. Report: root cause, fix applied, pass/fail result

COMMON FAILURE PATTERNS:
┌─────────────────────────────────┬──────────────────────────┬────────────────────────────┐
│ Error                           │ Likely Cause             │ Fix                        │
├─────────────────────────────────┼──────────────────────────┼────────────────────────────┤
│ Timeout: toBeVisible            │ Selector wrong/not render│ MCP inspect, update locator│
│ strict mode violation: N elems  │ Selector too broad       │ Make selector more specific│
│ expect(received).toBe(expected) │ App behavior changed     │ Update page obj or testdata│
│ Timeout: toBeEnabled            │ Element not interactive  │ Better wait in page obj    │
│ page.goto: net::ERR_*           │ URL wrong / staging down │ Fix allURL.ts or retry     │
│ Flaky (passes sometimes)        │ Race condition           │ Add expect.poll(), proper  │
│                                 │                          │ waits                      │
└─────────────────────────────────┴──────────────────────────┴────────────────────────────┘

2-ATTEMPT DEBUGGING RULE:
  If the same root cause error appears after 2 fix-and-rerun cycles:
  - STOP — do not make a 3rd speculative fix
  - Report: exact error + attempt 1 + attempt 2 + diagnosis + what is needed
  - This prevents wasting time on fixes that don't address root cause

================================================================================
 12. LOCATOR PRIORITY STRATEGY
================================================================================

USE IN THIS ORDER (most preferred first):

  1. getByTestId('data-testid-value')
     Best: stable, developer-controlled, immune to UI changes
     Use when: HTML has data-testid attributes

  2. getByRole('button', { name: 'Submit' })
     Best: accessible name is stable, resilient to class/style changes
     Use when: buttons, links, headings, checkboxes, textboxes with roles

  3. getByLabel('Email address')
     Best: tied to form semantics, works with aria-label too
     Use when: form fields with <label> elements

  4. getByPlaceholder('Enter your email')
     Good: often stable for input fields
     Use when: inputs with placeholder attributes

  5. Stable CSS selectors
     Acceptable: input[name="email"], [data-cy="submit"], .submit-button
     Use when: semantic selectors are unavailable

  NEVER USE:
  - Dynamic IDs (#ember123, #react-select-2-input) — change on every render
  - XPath — fragile, verbose, hard to maintain
  - nth() or index-based selectors — break when data changes
  - .css-class that is generated (e.g., CSS-in-JS hashes)

COMMON LOCATOR PATTERNS:
  // Role-based (preferred for interactive elements)
  page.getByRole('button', { name: 'Save' })
  page.getByRole('link', { name: 'Dashboard' })
  page.getByRole('textbox', { name: 'Search' })
  page.getByRole('checkbox', { name: 'Remember me' })
  page.getByRole('combobox', { name: 'Country' })

  // Filtering for specificity
  page.getByRole('alert').filter({ hasText: 'Success' })
  page.locator('.modal').getByRole('button', { name: 'Confirm' })

  // Exact text matching (prevents substring traps)
  page.getByText('Active', { exact: true })
  page.getByRole('button', { name: /^Active/ })  // regex anchor


================================================================================
 13. WAIT STRATEGIES
================================================================================

CORRECT WAIT PATTERNS:
┌───────────────────────────────────┬────────────────────────────────────────┐
│ Strategy                          │ When to Use                            │
├───────────────────────────────────┼────────────────────────────────────────┤
│ waitUntil: 'domcontentloaded'     │ Initial page navigation                │
│ await expect(locator).toBeVisible │ Wait for element to appear             │
│ await expect(locator).toBeEnabled │ Wait for element to be interactive     │
│ await expect.poll(() => fn)       │ Wait for a value to change             │
│ await page.waitForURL(/pattern/)  │ Wait for navigation to complete        │
│ waitForLoadState('networkidle')   │ After actions that trigger data reload │
│   .catch(() => {})                │ (MUST wrap in catch — may not settle)  │
└───────────────────────────────────┴────────────────────────────────────────┘

NEVER USE:
  page.waitForTimeout(5000)  — flaky, slow, masks real issues

ASSERTION-BASED WAIT (preferred over network waits):
  // Fragile
  await page.waitForLoadState('networkidle');
  await button.click();

  // Robust — waits for actual element state
  await expect(button).toBeEnabled({ timeout: 60000 });
  await button.click();

DYNAMIC DATA (use expect.poll):
  // Fragile — checks once, may race with loading
  const count = await getRowCount();
  expect(count).toBe(5);

  // Robust — retries until condition is met
  await expect.poll(() => getRowCount(), { timeout: 30000 }).toBe(5);

NETWORKIDLE (always wrap):
  // Staging may never fully settle — always use with catch
  await page.waitForLoadState('networkidle', { timeout: 10000 }).catch(() => {});

 14. TEST RELIABILITY PATTERNS
================================================================================

REACT-SELECT / AUTOCOMPLETE FIELDS:
  await fieldLocator.click();
  await fieldLocator.fill('');
  await fieldLocator.pressSequentially(searchText, { delay: 100 });
  const option = page.getByText(optionText, { exact: true });
  await option.first().waitFor({ state: 'visible', timeout: 10000 });
  await option.first().click();

GUARD AGAINST FLAKY CLICKS:
  await expect(button).toBeEnabled({ timeout: 60000 });
  await page.waitForLoadState('networkidle', { timeout: 30000 }).catch(() => {});
  await button.click();

SUBSTRING MATCHING TRAPS:
  // Bad — ":has-text('Active')" matches "Inactive" too
  page.locator('button:has-text("Active")');

  // Good — exact match or regex anchor
  page.getByRole('button', { name: /^Active/ });
  page.getByText('Active', { exact: true });

ACCESSIBLE ROLE SELECTORS (resilient to style changes):
  // Bad — CSS class may change
  page.locator('button.btn-primary');

  // Good — accessible name is stable
  page.getByRole('button', { name: 'Save' });

WHEN A TEST FAILS — DIAGNOSTIC PROCESS:

  1. READ THE ERROR CAREFULLY
     - What line failed?
     - What assertion failed?
     - Is it a timeout, strict mode violation, navigation error?

  2. CHECK KNOWLEDGE LAYERS FIRST (before MCP)
     - Is this a known quirk in page-knowledge.json?
     - Is the locator outdated in src/locators/?
     - Is the page object method wrong in src/pages/?

  3. USE MCP IF NEEDED (when error is unclear or selector needs inspection)
     - browser_navigate to the failing URL
     - browser_snapshot to see current DOM
     - browser_click / browser_type to verify interactions

  4. FIX IN CORRECT LAYER
     - Selector wrong → src/locators/<feature>.locators.ts
     - Wait logic wrong → src/pages/<feature>.page.ts
     - Test data wrong → src/data/testdata.json
     - URL wrong → src/data/allURL.ts
     - Test flow wrong → src/tests/<feature>.spec.ts (last resort)

  5. RE-RUN SPECIFIC TEST
     npx playwright test src/tests/<file>.spec.ts -g "TCXX" --project=chromium

  2-ATTEMPT RULE:
  If same root cause error after 2 fix cycles:
  - STOP immediately
  - Report: exact error + attempt 1 + attempt 2 + diagnosis + what is needed
  - Do not make a 3rd speculative fix

USEFUL DEBUG COMMANDS:
  npx playwright test --debug                  # step-through debugger
  npx playwright test --headed                 # see browser
  npx playwright codegen https://your-app.com  # record interactions
  npx playwright show-trace path/to/trace.zip  # view detailed trace


================================================================================
 20. KNOWLEDGE LAYER SYSTEM
================================================================================

PURPOSE: Check what you already know before using MCP (browser inspection).
         Each layer builds on the previous. Only go to the next when the
         current layer doesn't have what you need.

LAYERS IN ORDER:

  Layer 1: test-management/page-knowledge.json
  ─────────────────────────────────────────────
  Primary knowledge base. Contains per-page entries:
  - interaction_patterns: How to operate complex widgets
  - behavioral_notes: What the app does in specific scenarios
  - known_quirks: Timing issues and proven fixes
  RULE: If documented here, do NOT use MCP.

  Layer 2: src/locators/*.locators.ts
  ────────────────────────────────────
  Source of truth for element selectors.
  Before defining any new locator, check if it already exists here.

  Layer 3: src/utils/*.ts
  ────────────────────────
  Shared helper functions. Check here before writing any helper logic.
  If a similar function exists, use it.

  Layer 4: src/pages/*.page.ts
  ─────────────────────────────
  Reusable interaction logic. Check here and app-config.md before
  writing any new methods.

  Layer 5: src/tests/*.spec.ts
  ─────────────────────────────
  Existing test patterns to reference. Check how similar scenarios
  were structured (serial mode, beforeEach navigation, polling, etc.)

  Layer 6: Playwright MCP (LAST RESORT)
  ──────────────────────────────────────
  Use ONLY when layers 1-5 don't have what you need:
  - Page has no entry in page-knowledge.json
  - Needed selector doesn't exist in locator files
  - Widget interaction pattern is unknown

AFTER MCP DISCOVERY — ALWAYS UPDATE:
  1. Add interaction patterns/behaviors/quirks to page-knowledge.json
  2. Add new locators to src/locators/<feature>.locators.ts
  3. Add new methods to src/pages/<feature>.page.ts

KNOWLEDGE BASE UPDATES ARE ALSO REQUIRED WHEN:
  - You fixed a non-obvious test failure
  - You discovered a DOM ordering quirk
  - You found a timing issue with a specific widget
  - You learned a validation rule or default value behavior
  Any non-obvious finding during implementation belongs in page-knowledge.json.
